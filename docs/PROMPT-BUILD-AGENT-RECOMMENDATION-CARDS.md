# تكليف وكيل منصة البناء — تحسين تصميم جميع بطاقات التوصيات فقط

**المستودع:** `bob66aker-cpu/al-mustashar`  
**الفرع الإلزامي:** `experimental-v2-2026-10-25`  
**نسخة الحماية:** `release-1-pre-oct11-preserved` عند الالتزام `536244cb5b57f788afa15ccbe59659ef9f80dc12`  
**النطاق:** تصميم وتنسيق وألوان جميع بطاقات «التوصيات الزراعية» في قسم `#/tws` فقط. لا توسّع النطاق من تلقاء نفسك.

## المهمة المطلوبة

نفّذ تحسينًا بصريًا متكاملًا ومتسقًا لجميع بطاقات التوصيات الـ258، بما فيها البطاقات التي لم يصل إليها التحسين السابق، مع إبقاء المحتوى والبيانات كما هي حرفيًا. المطلوب واجهة عربية RTL احترافية وواضحة، أنيقة للمزارع البسيط ومفيدة للمحترف، باستخدام مبادئ Bento Grid 2.0 وGlassmorphism/Liquid Glass بشكل معتدل وقابل للقراءة، لا مؤثرات مبالغًا فيها.

## قيود غير قابلة للتفاوض

1. **ممنوع تعديل البيانات أو النصوص الزراعية أو تصحيحها أو إعادة توليدها.** لا تغيّر أي ملف داخل `data/` أو `data/tws/`، ولا الأسماء أو الأرقام أو ترتيب الكتاب أو قيم المادة الفعالة أو التركيز أو التركيبة أو معدل الاستخدام أو WHO أو فترة الأمان أو CAS أو أرقام الصفحات.
2. لا تحذف بطاقة أو محصولًا أو إصابة أو صورة أصلية، ولا تختصر محتوى أي بطاقة. لا تستبدل صورة كتاب بصورة مولّدة أو من الإنترنت.
3. لا تغيّر منطق البحث أو التصفية أو التوجيه أو مصدر البيانات أو قواعد المطابقة أو حالة التحقق.
4. لا تعدّل `main` أو `work-branch` أو فرع الإصدار الأول المحفوظ، ولا تدمج ولا تنشر ولا تطلق إصدارًا عامًا. العمل محصور في الفرع التجريبي المذكور.
5. لا تحذف فروعًا أو وسومًا أو ملفات، ولا تغيّر إعدادات الاستضافة أو النطاق أو CI دون ضرورة وموافقة مستقلة.
6. لا تضف خطوطًا أو مكتبات أو موارد خارجية؛ التطبيق يجب أن يبقى محليًا ويعمل دون إنترنت. التزم بـCSP والموارد المحلية الموجودة.
7. إذا اكتشفت مشكلة في البيانات أو النص العلمي، سجّلها منفصلة فقط ولا تصلحها ضمن هذه المهمة.

## الملفات التي يجب فحصها أولًا

- `index.html` لمعرفة نقاط تحميل الواجهة والأنماط العامة.
- `src/tawsiyat.js` لبناء واجهة بطاقات التوصيات.
- `src/tokens.css` لرموز الألوان والمسافات والطباعة والتباين.
- `src/i18n.js` وملفات تسميات `data/tws/labels.json` للقراءة فقط، للتحقق من أن التصميم لا يكسر التسميات متعددة اللغات.
- اختبارات التوصيات والمتصفح ذات الصلة، بما فيها `tests/tawsiyat.test.mjs` إن كان موجودًا و`npm run test:static` و`npm run test:browser` و`npm run test:a11y` بحسب بيئة المشروع.

لا تفترض أن أسماء الفئات أو أماكن الأنماط كما تتوقع؛ افحص التنفيذ الفعلي في هذا الفرع قبل التعديل.

## متطلبات التصميم

- بطاقة موحدة بصريًا لكل الإصابات والمنتجات، مع تسلسل واضح: اسم المحصول/الإصابة، بيانات المصدر ورقم الصفحة، وصف الإصابة، ميعاد الظهور، توقيت المكافحة، الإرشادات، ثم جدول التوصيات/المواد.
- استخدام ألوان زراعية راقية (أخضر عميق وأخضر فاتح مع درجات محايدة) وتدرج بصري هادئ؛ Glassmorphism خفيف على الأسطح فقط، مع خلفية وحدود تضمن وضوح النص.
- تمييز الأقسام بعناوين وأيقونات متسقة؛ لا تعتمد على اللون وحده لإيصال المعنى. لا تخترع رموزًا توحي بأن حالة علمية أو تنظيمية مؤكدة.
- تنظيم جدول المواد على هيئة خلايا/صفوف متجاوبة، مع إبقاء كل قيمة كاملة؛ على الشاشات الصغيرة يمكن أن تتحول الصفوف إلى مجموعات رأسية بدل قص النص أو إخفائه.
- معالجة النص العربي الطويل، والأسماء العلمية اللاتينية، والأرقام والوحدات وCAS وRTL/LTR باستخدام `unicode-bidi` و`overflow-wrap` عند الحاجة دون قلب ترتيب المحتوى.
- تحسين التباعد، والحواف، والظلال، وحالات hover/focus/active، وانتقالات قصيرة؛ احترام `prefers-reduced-motion`.
- الحفاظ على وضوح شارات «يحتاج تحققًا» وبيانات المصدر؛ لا تجعل الزخرفة تضعف معنى الشارة.
- لا تستخدم صورًا أو زخارف داخل البطاقة إلا إذا كانت موجودة أصلًا ومرتبطة بالمصدر. اجعل الألوان والخطوط متناسقة مع رموز التصميم الحالية بدل تكرار ألوان خام متفرقة.
- تأكد من العرض على الهاتف الضيق (320–360px)، الهاتف الحديث، الجهاز اللوحي، وسطح المكتب؛ لا يوجد تمرير أفقي للصفحة ولا تداخل أو قص أو ارتفاعات ثابتة تحجب النص.
- لا تغيّر التصميم العام لأقسام فحص المبيدات أو OCR أو الصفحة الرئيسية؛ الهدف حصريًا بطاقات التوصيات.

## طريقة العمل الإلزامية

1. سجّل commit البداية واسم الفرع، وافحص الفرق عن نسخة البداية.
2. حدّد كل قواعد CSS ومكوّنات العرض التي تؤثر فعلًا في بطاقات `#/tws`. ميّزها عن بطاقات قسم «الإرشاد» الآخر حتى لا تتغير واجهات غير مقصودة.
3. عدّل طبقة العرض فقط، بأقل عدد ممكن من الملفات. لا تغيّر أي ملف بيانات.
4. أضف/حدّث اختبارات تحقق آلية للتأكد من أن محتوى البيانات وعدد البطاقات وترتيبها لا يتغير. يجب أن تكون المقارنة قبل/بعد مبنية على بصمة الملفات المرجعية أو فحص آلي واضح.
5. شغّل الاختبارات المتاحة وسجّل الأمر والنتيجة الفعلية لكل اختبار؛ لا تكتب «ناجح» دون تشغيله. إذا لم تتوفر بيئة متصفح، اذكر ذلك صراحةً ولا تدّعِ التحقق البصري.
6. افحص يدويًا أو عبر screenshots عينات من بطاقة قصيرة، وبطاقة طويلة، وبطاقة تحتوي جدول مواد متعدد الصفوف، وبطاقة بها «يحتاج تحققًا»، على الهاتف وسطح المكتب. تحقق من العربية واللاتينية والصور وأرقام الصفحات.
7. راجع `git diff --check` والفرق كاملًا. أي تغيير في `data/**` أو محتوى التوصيات يُعدّ فشلًا ويجب التراجع عنه.
8. نفّذ commit برسالة واضحة على الفرع التجريبي فقط، ثم قدّم تقريرًا نهائيًا.

## معايير القبول

- [ ] لا تغيير في أي بيانات/نصوص/صور مرجعية أو ترتيب أو عدد البطاقات.
- [ ] لا ملفات بيانات معدّلة، ويُذكر عدد الملفات المتغيرة ومساراتها.
- [ ] لا انكسار في RTL/LTR أو النصوص الطويلة أو الجداول على الهاتف.
- [ ] تباين مقروء وحالات التركيز وإمكانية الوصول لا تتراجع.
- [ ] اجتياز الاختبارات ذات الصلة مع نتائج موثقة.
- [ ] لا نشر ولا دمج ولا تغيير على الإصدار الأول أو فرع الإنتاج.
- [ ] رابط commit والفرع وقائمة الملفات والاختبارات والمشكلات المتبقية في التقرير.

## صيغة التقرير النهائي المطلوبة

1. الفرع وcommit البداية والنهاية.
2. الملفات التي تغيرت ولماذا.
3. تأكيد صريح بأن `data/**` لم تتغير، مع نتيجة فحص الفرق.
4. أوامر الاختبارات ونتيجة كل أمر.
5. لقطات شاشة/روابط معاينة إن كانت البيئة تدعمها، وإلا التصريح بعدم توفرها.
6. قائمة بأي بطاقة/حالة لم يتم التحقق منها، دون ادعاء اكتمال شامل.
7. تأكيد أن التغييرات تجريبية وغير منشورة.
